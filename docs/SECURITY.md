# Security model and integration limits

## Boundaries and operating assumptions

The authorized operator controls the calling Python process, policy, keys, clock, local SQLite files and all `Store` administration calls. The local `Sandbox` operates on the same trusted database and is not an operating-system sandbox, network gateway, hardware interlock or real device driver. Anyone who can bypass it or alter files and process memory can bypass the controls. This code cannot force all paths to a real actuator through the gate. It is research software for controlled experiments only.

An allow response states that the supplied data passed the configured checks at that point. It is not proof of physical safety, sensor accuracy, task alignment, protection against all prompt injections, or actual human review. A signed but incorrect sensor observation can still cause a wrong action; the included experiment explicitly demonstrates that failure. The local LLM adapter does not detect prompt injection or establish provenance of telemetry.

## Configuration and keys

Provide nonempty agent and reviewer mappings of principal -> key ID -> bytes, with each secret generated using a cryptographically secure generator and at least 32 bytes. Use separate keys for each principal, role and key version; length validation cannot measure entropy. The software rejects reuse within a keyring and across currently active gate and evidence configurations sharing the same database. It stores a role-independent HMAC-derived key fingerprint, not the key itself. Fingerprints are susceptible to guessing when secrets have low entropy and do not replace secure key generation. Keep secrets in an appropriate operator-controlled secret store rather than source code, logs or result files. The shared-secret mechanism cannot provide non-repudiation, individual identity, hardware attestation or proof of a human action.

Construct a `Store(path, create=True)` only for a genuinely new persistent local database; `Store(path)` opens an existing initialized database and never creates a missing file. Then populate the simulated inventory through trusted administrative calls, construct a `Gate` with an explicit policy and keyrings, then call `gate.activate_configuration()` through a trusted operator. Construct an `EvidenceIngestor` with explicit source keys and device grants and activate it separately before using signed evidence. The demo shows fixture setup; `tests/test_security.py` demonstrates the APIs.

Every activation atomically increments a generation and writes a digest of policy and key commitments into the shared database. Existing workers and pending decisions are bound to their generation; even reactivating identical settings or switching A to B and back to A does not revive older authorizations. Workers must be constructed after the intended activation, or the activating worker can continue with the new generation. Evidence has a separate generation. Configuration activation itself is privileged, and the database and operator remain trusted: an attacker who can call activation or rewrite the database can defeat this mechanism. This is not a distributed key management or consensus system. All workers must use the same protected database and a consistent clock.

## Configuration digest syntax

The low-level trusted activation API now requires a string containing exactly 64 ASCII hexadecimal characters, accepting either case and storing lowercase. Validation precedes clock invocation and the configuration transaction. Malformed digest rejection therefore does not update the active configuration, key rows, generation, decisions, clock mark or audit log. No clock observation is fabricated for a preflight input error. Later credential-reuse rejection still follows the existing savepoint and time-persistence behavior.

A version-0.20 local counterexample used the public administration API, unchanged credentials and no direct SQL writes. A 64-character digest with two trailing whitespace characters decoded to 31 bytes but was accepted, advanced the generation and left the prior gate inactive. The correction prevents that malformed activation. It does not authenticate the operator, verify that an otherwise valid digest describes the intended configuration, or demonstrate a remotely exploitable authorization bypass. The process, administrative API and database remain trusted.

Older malformed activations are not automatically rewritten or reversed. The earlier audit event can be hash-consistent while the active configuration is unusable, and audit-chain verification does not attest configuration health. Recover through a deliberate high-level activation of the assessed configuration, accounting for generation invalidation and fresh-evidence requirements. Reopening alone is not recovery.

## Approval integer boundary and input exceptions

Signed approval context versions are exact integers in the inclusive range 1 through 9,223,372,036,854,775,807, matching the signed integer range used for persisted versions. Booleans, non-integers and out-of-range values fail schema validation before canonical serialization or key authentication. This avoids serializing arbitrary-size versions that cannot represent supported context. It does not bound all caller allocations, establish an integer's provenance or promise general denial-of-service resistance. Clients must preserve integer values exactly when constructing HMAC input.

Handled input exceptions in `Gate.evaluate` and `Gate.approve` preserve the latest valid clock reading available to their denial path. The rejection transaction compares that reading with persistent time state, then reads the clock under its lock. A backward or failed later read keeps the request denied and can commit the earlier valid high-water mark without appending a denial event. Persistence still depends on successful storage and commit. If no valid clock was observed, no reading is fabricated.

A controlled counterexample in version 0.17 used an ordinary direct-API approval dictionary with a very large integer, an invalid reviewer signature, and clock rollback during processing. On Python configured with a finite integer-string limit, canonical serialization raised before authentication; the exception handler discarded the first valid clock reading, and an undelivered request expired at that reading could later be allowed. Version 0.18 rejects the impossible version before serialization and preserves valid time on the remaining handled input-exception paths. This is a local dependency-fault scenario under the documented trusted-clock assumptions. It is not evidence of a deployed network attack; observations already lost by earlier versions cannot be reconstructed.

## Replay, time and storage

A credential-reuse rejection during configuration activation preserves the active digest, generation and key registrations while retaining a valid clock observation. A savepoint rolls back the attempted registration independently of the outer clock and audit transaction. The outer transaction commits `configuration_rejected` with the configuration kind and `secret_reuse` code before the API raises `ValueError`. No secret or key fingerprint is included in that event. A pending or approved decision is not invalidated solely by the rejected configuration attempt, but expiry, context and other existing checks still apply. A worker that captured an older time before waiting for this transaction must pass the usual high-water check after acquiring the lock.

This persistence is conditional on successful storage and commit. Clock failure before a valid observation, unavailable storage, failed audit writing, process interruption or a commit error can prevent the mark and event from being recorded. Rejections observed only by an older version are not reconstructed. Incorrect forward time can reduce availability; operators must assess clocks and recovery state rather than erase the mark or replay history.

Proposal, approval and evidence nonces are scoped by kind and principal and inserted atomically under `BEGIN IMMEDIATE`; a unique database constraint rejects duplicates across processes on the same database. Request IDs are unique per agent, not globally. Approval lookup and simulated execution explicitly include `agent_id`, which is also covered by the signed approval. This avoids collisions but does not authenticate the calling process or make `agent_id` a secret. Nonce rows are kept for an additional 86,700 seconds after their stored expiry: the maximum currently supported TTL (86,400 seconds) plus clock skew (300 seconds). All proposal, approval and evidence paths use the same delayed cleanup, so an existing record is retained while a previously used message might become valid under a later supported timing configuration. This does not extend message validity, reconstruct rows already pruned by older versions, or prevent acceptance of previously unseen messages after a timing window is enlarged. If earlier replay history is uncertain, rotate affected keys and assess outstanding messages before widening timing settings. Use fresh nonces; longer retention increases storage. Authorization, approval, evidence and simulated execution compare clock readings made before and after acquiring the write lock; execution checks again shortly before its database update. A persistent high-water mark records the higher observed value and fails closed on backward movement, including between those two reads or after restart. The check can conservatively deny under concurrent interleaving when one worker observes an older time before another commits a newer one. Ordinary exceptions raised by the configured clock provider are treated as clock failures: decisions and evidence are denied, simulated execution is refused, and configuration activation fails. Valid pre-lock observations are persisted before a second clock read; if the second reading fails, the requested action remains denied while the earlier high-water observation can be committed. Early denials and stale-configuration denials likewise update the high-water mark when the transaction succeeds. Failed clock readings, rollback or storage errors may prevent denial logging; audit sequence, not wall-clock time, establishes entry order. Availability is reduced until the clock catches up or the trusted operator recovers state. This is best-effort local checking, not a hard real-time guarantee or an authenticated time source. Independent databases do not share replay state.

Version 0.22 opens intact version-0.21 and version-0.20, version-0.19, version-0.18, version-0.17, version-0.16, version-0.15, version-0.14, version-0.13, version-0.12, version-0.11, version-0.10 and version-0.9 schema-5 databases, but refuses missing, empty, earlier-schema and structurally incomplete databases. New databases require the explicit, exclusive `create=True` option; a deleted file is not recreated by later connections. On open, the key-fingerprint uniqueness check requires a non-partial unique index; a partial index alone cannot enforce separation across roles and is rejected. On open and during clock checks, an existing high-water mark must be an integer from 0 through 4,102,444,800 inclusive; an out-of-range or invalid value fails closed without automatic repair. A missing mark also fails closed when any inventory, nonce, decision, audit, configuration or other metadata state remains. An initialized empty store can create its first mark. If all detectable state has also been removed, absence alone cannot distinguish loss from a fresh store. This validation cannot establish that an in-range value is true or detect every corruption or malicious rewrite. SQLite errors return a denial. The file is created with owner-only permissions where supported, but operators must secure its directory, backups, filesystem, side files and secrets, and must not treat permissions as complete isolation. Audit records and decisions accumulate without built-in retention, quotas or rate limiting. Capacity, backup, recovery and denial-of-service resistance are not validated for production. Do not delete replay or decision state as an ad hoc recovery technique while requests remain valid.

## Trusted inventory input

`Store.put_device` accepts device identifiers of 1–128 ASCII letters, digits, `_`, `.`, `:`, or `-`, consistent with the policy and message validators. `now` and `observed_at` must be exact integer Unix seconds from 0 through 4,102,444,800 inclusive. Booleans, negative values and values outside the range, including typical millisecond timestamps, are rejected before database changes. A future observation that is inside this range may be stored; the gate returns `invalid_context_time` until its clock reaches that observation. These checks prevent certain input errors but do not authenticate an operator, identify every incorrect unit or establish sensor truth.

## Evidence, review and simulated execution

An authenticated, authorized observation at the stored timestamp with a different signal sets the context to `unknown`, increments its version, and returns `accepted: true, code: evidence_conflict`. It does not assert that the incoming signal is true. The derived conflict state uses an empty `source_id` and a digest of a conflict record, not the signed digest of one sensor report. The audit event includes the previous context and incoming digest; those digests do not prove the physical observations. Additional same-time disagreements remain unknown. Identical same-time reports and strictly older reports are rejected; a strictly newer eligible observation may replace the unknown state. Trusted administrative context updates may override it.

This rule covers only reports equal to the currently stored observation time. It does not wait for other sensors, detect every disagreement across timestamps, establish a quorum, or reverse an effect that was already simulated. Previously ignored reports cannot be reconstructed automatically from older rejection records.

Evidence needs a valid source key, explicit source-to-device grant, valid times and fresh nonce; older observations are rejected. It cannot change device criticality. Each signed or derived conflict context records the active evidence generation. If the evidence configuration is activated again, older signed contexts are no longer sufficient for quarantine or restore, and pending or approved actions depending on them cannot execute. This conservative invalidation applies even when an unrelated source changes; fresh evidence is needed. Inspection does not require signal evidence. A valid MAC shows only that the key holder sent the observation, not that the physical reading is true. Trusted administrative context updates increment the version and replace prior source attribution; they are a separate trust path rather than verified sensor readings.

Only a `review_required` decision can be signed by a separately keyed reviewer explicitly granted that action and target under `review_grants`. An identical agent/reviewer identifier is rejected even if the keys differ. The gate creates a random 256-bit review challenge for each pending decision; the reviewer signs it together with the agent and request identifiers, request and policy digests, context version, reviewer identity, issue time and nonce. An approval timestamp earlier than the decision is rejected. These mechanisms bind a signed approval to a generated decision, but identifier comparison cannot detect one person controlling different identities, and the key does not prove that a human reviewed anything. Hard denials and stale/conflicting evidence cannot be overridden. The broker rechecks the reviewer grant and current state in a transaction and consumes the authorization once. These guarantees cover only the local simulated database, not an external device or process.

## Audit records

Built-in audit entries are SHA-256 chained and link request, policy, approval and execution using digests and context/generation identifiers; they do not intentionally record secrets or free-text reasons. They do include agent, reviewer, source, device and action identifiers, which may themselves be sensitive. Early evidence rejections are recorded when the clock is valid, has not rolled back and the store is available. Failed storage or an unusable clock can prevent a denial from being logged, so this is not a complete external audit service. Each new database has a random audit identity bound to its chain. After verifying a nonempty log, `Store.audit_checkpoint()` returns its identity, sequence and hash; retain this checkpoint independently in trusted storage. `Store.verify_audit(checkpoint=checkpoint)` checks that prefix even after valid appends, while `verify_audit(expected_head=...)` requires an exact current head. A checkpoint protects only its anchored prefix: a later unanchored suffix can be rewritten and recomputed, and a checkpoint created after tampering cannot prove earlier authenticity. There is no built-in external anchor, trusted timestamp, append-only service or log signing.

Each `Store` pins its audit identity for the object's lifetime. High-level read/write transactions and audit verification check the current connection's identity against that pin in the same SQLite snapshot. Different-identity replacement or symlink retargeting is rejected even without a required checkpoint; these are local continuity checks, not proof that the database contents are authentic. `StoreIdentityError` is a `ValueError` subclass used by direct state access; `verify_audit` instead reports `database_identity_changed`. A mismatch prevents normal denial logging to the replacement file. Raw connections and direct SQL bypass the check.

The pin is held only in memory. A same-identity older snapshot, copied audit identity, or deliberate new `Store` is not sufficient evidence of continuity. Recent independently retained checkpoints and trusted recovery procedures remain necessary, and checkpoints do not authenticate other state tables. Stop workers and SQLite connections before recovery; the tests replace files between completed transactions and retarget symlinks, and do not validate live replacement during active database access.

### Read-only file inspection

`Store.verify_audit_file` and `verify-audit` provide a separate read-only inspection path for schema-5 files. They use one SQLite read transaction through a `mode=ro`, query-only connection, including for a supplied prefix checkpoint and exact expected head together. The file path is encoded as a SQLite URI; missing files are not created and unsupported schemas are not initialized or migrated. An empty initialized audit chain can be consistent without being independently anchored. A reserved application write lock does not require the inspector to acquire another write lock; ordinary SQLite read locking and WAL side-file requirements still apply. A busy or unavailable file can cause verification to fail.

The result's `scope` is `audit_chain_only`. This path deliberately does not construct a normal `Store`, validate application tables or clock state, install a required checkpoint on workers, or pin identity across invocations. Passing inspection is not evidence of current replay history, trustworthy inventory, or the absence of a stale same-identity snapshot. An unanchored result checks only chain consistency. Even an anchored result depends on a genuinely independent, trustworthy anchor and covers only its described prefix or exact head. The report does not validate audit-event semantics or authenticate physical observations. Inspection never repairs a file.

CLI verification failure returns JSON with exit status 1; malformed command or checkpoint input returns status 2. The bounded checkpoint parser rejects duplicate fields, null and invalid objects, and input exceeding 65,536 bytes. A malformed requested checkpoint must not silently remove anchoring. Hash and head mismatches now include explicit codes, `audit_hash_mismatch` and `expected_head_mismatch`, in the existing and file-verification APIs. These codes describe failed checks; they do not attribute an incident to an attacker.

### Optional enforced checkpoint and recovery

A caller may pass an independently retained `required_checkpoint` to `Store(existing_path, required_checkpoint=checkpoint)`. Opening validates the checkpoint in the initialization transaction. Thereafter guarded read and write transactions verify the chain in the same SQLite transaction before state is read or modified. Invalid, missing, or older-than-checkpoint chains fail closed; creating a new database together with a checkpoint is rejected. Calling `verify_audit(checkpoint=other)` on a guarded store checks the required and caller-supplied anchors in the same SQLite snapshot; a different supplied checkpoint cannot override the required one. Successful dual verification includes `required_anchored_through` in the result. The default is **no required checkpoint**, so independent retention and enforcement by every participating worker are operator responsibilities. Raw `Store.connect()` and other direct database access bypass the guard; do not mix guarded clients with older or unguarded workers if enforcement is required. Expected heads are validated as lowercase SHA-256 hexadecimal strings. Checkpoint values are copied and normalized before comparison; a guarded verification with an additional checkpoint always checks the required anchor first and scans the chain twice in the same SQLite snapshot. This addresses misleading custom Python equality behavior, not an adversary who controls the process or database.

The checkpoint anchors only audit records through its sequence. It does not attest other tables, stop a hostile database writer, or protect a rewritten suffix after that sequence. An old but valid checkpoint may also allow restoration of a snapshot newer than the checkpoint but older than recent replay state. Safe replacement while SQLite connections remain active, protecting the independently retained checkpoint, securely maintaining backups and recovering credentials are outside the tested security boundary. After a reset or potentially stale restoration, rotate affected credentials and assess outstanding signed messages; do not assume checkpoint verification restores lost nonce history. The check scans the full current audit chain on each guarded transaction, so cost and availability worsen as logs grow; use the separately reported local microbenchmark only as an illustration, not a deployment bound.

## Optional loopback model connection

The adapter connects directly to a validated numeric loopback HTTP endpoint and does not use proxies or follow redirects. It requires HTTP 200 for this non-streaming chat contract and rejects every other status before reading the body, including other 2xx statuses. It rejects oversized responses, bodies shorter than a declared Content-Length, duplicate Content-Length or Transfer-Encoding headers, concurrent Content-Length and Transfer-Encoding, invalid numeric lengths, and unsupported transfer encodings. This deliberately rejects even identical duplicate Content-Length fields. The client sends Accept-Encoding: identity and accepts only absent Content-Encoding or one identity value, ignoring ASCII case and surrounding spaces or tabs. Compressed encodings, lists and duplicate fields are rejected before JSON processing, including incorrectly labelled plaintext. No response decompression is provided. A valid chunked response or a close-delimited response can be processed. With no declared length and no chunk framing, syntactically complete JSON alone cannot prove that the sender transmitted the whole intended response. The official chat and error documentation describes a 200 chat response and JSON errors using the top-level `error` property (https://docs.ollama.com/api/chat; https://docs.ollama.com/api/errors). After bounded JSON parsing, any presence of that property rejects the response, regardless of value or otherwise valid completion fields. This is a conservative integration rule: compatible proxies that add `error: null` to successful replies or use a different 2xx status must be adjusted or are refused. Only the top-level property has this meaning; the word error in candidate reason text is ordinary untrusted text. The non-streaming response must declare `done: true` and an `assistant` message. If `done_reason` is present it must be `stop`; explicit length limits, missing completion flags and other finish reasons are rejected even if their JSON parses. These fields are service assertions and do not prove output truth, completeness of an untrusted service, or safety. A monotonic deadline with a socket-shutdown watchdog applies to the network request, including slow headers and slow response bodies; the deadline is best effort, depends on host scheduling and excludes local JSON parsing. It is not a hard real-time bound. Loopback does not authenticate the local service, sandbox the model, verify its output, or constrain any network behavior of the service itself. The local process and service remain under the operator's control.

A service-error rejection raises a fixed `ValueError` without echoing the error value. The CLI reports failure with exit status 2 and no candidate output. There is no automatic retry, cached candidate or model fallback. A failure before the trusted wrapper creates no proposal, gate decision or gate audit event; the gate log is not an operational log of all model-service failures. A response that passes these protocol checks is still untrusted and must follow normal wrapper, gate and simulated-broker checks. A fake-service counterexample in version 0.18 supplied a completion-shaped body with an error field, or HTTP 206 with a complete-looking body; the adapter returned a candidate. Version 0.19 rejects both. These tests do not establish that an actual Ollama release emits those contradictory replies, demonstrate an authorization bypass, or evaluate a real model.

## Serialization and interoperability

In the Python API, proposals, approvals, evidence and candidate dictionaries are detached before field validation. Proposal actions, approval verdicts and evidence signals must be ordinary string values after normalization; non-string objects are rejected before comparisons. Message values that are string subclasses are reduced to their underlying standard string value, and nonstandard string keys are rejected. Authentication and state processing use the same validated scalar snapshot. A caller racing a mutation may have either version captured; the selected snapshot must itself pass schema and MAC checks. Copying does not promise an atomic view of independently changing caller data or protect against malicious code in the trusted process. Callers should avoid mutating messages while submitting them.

A proposal envelope is `{"payload": {...}, "signature": "64 hex characters"}`. Payload fields are exactly `request_id`, `agent_id`, `key_id`, `action`, `target`, `nonce`, `issued_at`, and `reason`. The signature is HMAC-SHA256 over the payload serialized by Python `json.dumps(payload, sort_keys=True, separators=(',', ':'), ensure_ascii=True, allow_nan=False).encode('ascii')`; it is not RFC 8785 JSON canonicalization. Hexadecimal MACs accept either case and compare decoded bytes. UTF-8 input uses strict decoding; duplicate JSON object keys, malformed Unicode, unexpected fields and oversized envelopes are rejected. Text larger than the byte limit is rejected before allocating a UTF-8 copy, while shorter text is still checked against its encoded byte length. Size and Unicode checks use the underlying string or byte content rather than overridable subclass methods. Public fixture-only proposal, approval and evidence vectors, including Unicode and escaped text, are provided in `examples/signature_vectors.json`, with an optional Node.js verifier for these examples. They are a limited interoperability check, not proof for all inputs. Independently test the exact byte serialization for the integration in use. `sign()` is the Python reference implementation.
